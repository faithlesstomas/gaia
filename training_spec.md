# External Training Module Specification & Continuous Learning Loop

## Objective
Enable a **Python Training Node** to act as a self-improving "Brain" backend that not only serves LLMs via LiteLLM but also **trains** them on data generated by **GAIA** (the "Body").

## Architecture: The "Continuous Learning Loop"

```mermaid
graph TD
    GAIA[GAIA (Guile)] -->|1. Post Trajectories| TRAIN_API[Training API]
    TRAIN_API -->|2. Enqueue Job| WORKER[Training Worker (Unsloth)]
    WORKER -->|3. Fine-tune| MODEL[Base Model (Ministral-3b)]
    WORKER -->|4. Save Adapter| ADAPTER[LoRA Adapter]
    ADAPTER -->|5. Hot-Swap| LITELLM[LiteLLM Proxy / Inference Engine]
```

## Part 1: Training Module (`src/trainer`)

**Prompt for Developer:**
"Implement a new module `src/trainer` that provides an API for fine-tuning LLMs using Unsloth. This module must be standalone or part of the Python backend."

### Key Components

1.  **API Endpoints (`src/server/routers/train.py`)**:
    *   `POST /train/dataset`: Upload formatted ChatML data (from GAIA).
    *   `POST /train/start`: Trigger a training job.
        *   Params: `base_model`, `dataset_id`, `epochs`, `lora_rank`.
    *   `GET /train/status/{job_id}`: Monitor progress (streaming logs).
    *   `POST /models/reload`: Provide hook to restart/hot-swap LiteLLM configuration.

2.  **Training Worker (`src/trainer/worker.py`)**:
    *   Use `fastapi.BackgroundTasks` or `Celery` (if simple) / `RQ` (Redis Queue).
    *   **Logic**:
        1.  Load `Unsloth` / `FastLanguageModel`.
        2.  Load dataset (convert if needed).
        3.  Run `SFTTrainer`.
        4.  Save adapters to `~/.models/adapters/{job_id}`.
        5.  Update job status.

3.  **Dependency Isolation**:
    *   Training requires heavy libs (Unsloth, Triton, xformers).
    *   Ensure `import unsloth` happens *inside* the worker, not at server startup, to keep inference startup fast.

## Part 2: Hot-Swap Capability

**Challenge**: Ollama/LiteLLM doesn't easily support hot-swapping adapters programmatically without restart.
**Solution**: Implement an automated configuration reload for LiteLLM.

1.  **LiteLLM Reload logic**:
    *   Dynamically write the new adapter configuration to `litellm_config.yaml`.
    *   Send a SIGHUP or restart the LiteLLM process via a supervisor.

## Part 3: GAIA Integration (The "Body")

**Prompt for GAIA Developer:**
"Update GAIA to automatically push curated datasets to the Training node after a successful session batch."

1.  **Updates to `curator.scm`**:
    *   Add flag `--push-to-training <url>`.
    *   Use `guile-json` + `web client` to POST `dataset-success.jsonl` to `TRAINING_URL/train/dataset`.

2.  **Updates to `Makefile`**:
    *   `make learn`: Runs `make dataset` -> Pushes to Training API -> Triggers `POST /train/start`.

## Feasibility Analysis

### 1. Unified Repo vs. Separate Repo?
*   **Recommendation**: **Separate Repo / Standalone process** for Training.
*   **Why**: LiteLLM focuses on inference routing. The Training Worker should be a distinct microservice handling heavy PyTorch workloads.

### 2. MLIR/IREE for Training?
*   **Verdict**: **Too early**.
*   **Reason**: MLIR/IREE is excellent for *inference* optimization (compiling to bare metal/Vulkan). It is NOT yet a mature *training* stack for LLMs. You would lose the massive ecosystem of Hugging Face/Unsloth optimizers.
*   **Path**: Train in Python (Unsloth). Export to GGUF or compiled IREE artifact for Inference.

### 3. Automated Loop
*   **Feasibility**: High.
*   **Risk**: "Catastrophic Forgetting" or "Model Collapse" if training on bad data.
*   **Safeguard**:
    *   GAIA must validate data (already does via `FINAL` signal check).
    *   Keep a "champion/challenger" system:
        *   Train new adapter (Challenger).
        *   Run benchmark.
        *   If Benchmark > Current, promote to Champion.

## Implementation Steps (Prompt for Copilot/Dev)

**User Request**: "Add a training module backend."

**Strict Instructions**:
1.  Create `src/trainer` directory in a new Python project.
2.  Add `unsloth` to dependencies.
3.  Implement `TrainingService` class that wraps `SFTTrainer`.
4.  Expose `POST /train` endpoint in FastAPI.
5.  Implement a script to automatically patch `litellm_config.yaml` to include the new adapter.
